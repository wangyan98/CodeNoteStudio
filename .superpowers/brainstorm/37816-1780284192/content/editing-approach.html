How should users create and edit sequence diagrams?

This is the most fundamental design decision — it affects file format, editing UX, and rendering approach

A

Text-based DSL (like Mermaid)

Users write sequence diagrams in a text language. The editor renders a live preview alongside the code. Similar to how Markdown editors work — you write text on the left, see the diagram on the right.

Pros

  • Fast to type once you know the syntax
  • Git-friendly (plain text diffs)
  • Can leverage existing libraries (Mermaid.js)
  • Familiar pattern — same as MD editor in this project

Cons

  • Learning curve for syntax
  • No drag-and-drop convenience
  • Harder to rearrange participants visually
B

Visual drag-and-drop editor

A canvas-based editor where you drag participants onto the canvas, draw arrows between them, and edit labels inline. Similar to how the Mind Map editor works — direct manipulation of visual elements.

Pros

  • Intuitive — no syntax to learn
  • Immediate visual feedback
  • Easy to rearrange and reorganize

Cons

  • More complex to implement
  • JSON storage format — harder to diff in git
  • Slower for power users who know the syntax
C

Hybrid — DSL with visual helpers

Store as DSL text (like .seq.md or .seq.mermaid) with a live preview panel. Add toolbar buttons and autocomplete to help users write syntax — a middle ground between raw text and full visual editing.

Pros

  • Git-friendly plain text format
  • Toolbar/autocomplete lowers the learning curve
  • Power users can still type fast
  • Similar to existing MdEditor pattern

Cons

  • Still text-based — no true drag-and-drop
  • Preview may lag on large diagrams
